# 0003. 硬件端侧自治：数据平面直连云 + 控制平面经服务端，固件复刻三段式

- 状态：被 0005 取代（Superseded by 0005，2026-06-12）
- 日期：2026-06-11
- 相关：PRD §十二（硬件端侧自治）、§11.9（三段式而非 Realtime）、§11.12（Wi-Fi 优先 + BLE 网关）、§11.14（设备端 BLE 配网）；计划 `docs/design/plans/2026-06-11-on-device-autonomy.md`；ADR `0001`（ASR 失败不得断 `/ws`）、`0002`（全双工打断）

## 背景

当前架构是**服务端中心**：ESP32-S3 是瘦客户端，自建 FastAPI `/ws` 承担 ASR（火山 sauc）、LLM（Ark/Doubao）、TTS（seed-tts V3）、记忆（`memory/`）与 Agent 编排（`agent/graph.py`）。设备只做音频采集/播放与 UI。

新需求（PRD §十二）：**硬件只要联网就能独立完成整条语音交互**，不依赖自建服务端在运行链路中；记忆管理与语音交互核心搬到硬件；Web 控制台仍能连设备、同步记忆、管理并下发 key；且「服务端/Web 的核心链路与硬件复用、先 Web 调试再烧录」。

关键事实约束：ASR/LLM/TTS 都是**火山云端能力**，ESP32-S3 跑不动本地大模型。所以「独立」只能是**独立于自建服务端、设备直连火山云**，仍需联网；不是断网离线。

## 备选方案

- **A：维持服务端中心瘦客户端**（现状）。优点：编排/记忆只有一份 Python 实现，迭代快。缺点：设备必须依赖自建服务端在线，不满足「独立」。
- **B：端侧自治 + 双平面**（本 ADR 选定）。数据平面设备直连火山云跑三段式；控制平面保留一条到服务端的轻量长连接做 key 下发 / 记忆同步 / 远程命令；服务端 `/ws` 全链路保留为权威参考实现与 Web 调试宿主。固件以 C 复刻三段式 + 端侧记忆。
- **C：端侧用火山 Realtime 端到端**。设备只维护一条流式连接，固件最轻。缺点：与现有三段式链路不同、对 Prompt/安全/逐轮记忆注入控制弱；§11.9 已因此放弃 Realtime 作为主路径。
- **D：固件成为唯一权威实现，服务端退化为薄模拟器**。缺点：日常迭代变慢、Web 调试体验下降，违背「先 Web 调试再烧录」。

各备选在四个维度的取舍（◎好 ○中 △差）：

| 维度 | A 现状 | B 双平面(选) | C Realtime | D 固件权威 |
| --- | --- | --- | --- | --- |
| 联网即独立 | △ | ◎ | ◎ | ◎ |
| 逐轮记忆/安全可控 | ◎ | ◎ | △ | ◎ |
| 核心链路复用 / 先 Web 调试 | ◎ | ◎ | △ | △ |
| 维护成本（实现份数） | ◎ 一份 | △ 两份 | ○ | △ |

## 决策

采用 **B：端侧自治 + 双平面**，并锁定四项子决策：

1. **数据平面直连云、复刻三段式**：固件 C 分别直连火山流式 ASR 2.0 / Ark·Doubao / seed-tts V3，与服务端 `services/asr|llm|tts` 逐段对齐；**不**采用 Realtime 端到端（保 §11.9 逐轮记忆/安全可控）。
2. **控制平面经服务端**：设备保留一条到自建服务端的**轻量长连接（不带音频）**，复用现有设备注册表 + `/api/devices/{id}/*` 命令通道，下发 key、同步记忆、发远程命令；能穿透 NAT / 手机热点。
3. **Python 服务端为权威参考实现，固件为对齐它的 C 移植**：核心链路（编排 + 记忆）以服务端为准，固件照搬；用 **golden 测试向量**约束两端在同一输入下的检索结果 / 组装 Prompt / 记忆写入一致。日常**先 Web 调试，再烧录**。
4. **端侧 v1 即完整记忆智能**：端侧除短期窗口 + 本地检索打分外，**直接调用 LLM** 做画像/结构化记忆抽取，并每 20 轮做长期摘要（对齐 `profile_extractor` / `summary_store`）。代价计入固件工程量与端侧 token 成本。

配网沿用 §11.14 并硬化为「BLE 配对手机 → 手机 Wi-Fi/热点下发凭据」。

## 后果

- 正面：
  - 设备联网即独立交互，自建服务端不在语音运行链路上（可离线/可迁移）。
  - 控制平面复用现有注册表与命令通道，Web「连设备 / 同步记忆 / 管 key」落地成本低。
  - 服务端 `/ws` 全链路保留，「先 Web 调试再烧录」与「真机模拟器」不受影响。
- 负面 / 代价：
  - **编排 + 记忆存在两份实现（Python 权威 + C 移植）**，这是本架构最大的长期成本与一致性风险；缓解手段是把端侧编排做**薄而 spec 驱动** + golden 向量回归。
  - 固件需在 C 里实现 **3 个流式云客户端（含 TLS + 火山自定义二进制协议）+ 端侧记忆存储 + LLM 抽取/摘要触发**，是显著工程量。
  - 端侧记忆智能完整化带来额外端侧 LLM 调用与 flash 读写压力；flash 容量/写寿命需评估，必要时扩分区/挂 SD。
  - key 下发到端侧增加密钥分发面，需经鉴权控制平面 + NVS，落地时单列安全边界。
- 后续关注：
  - golden 向量的覆盖面与两端漂移检测机制。
  - 记忆双向同步的方向与冲突策略（版本/时间戳），避免覆盖丢数据。
  - 端侧三段式的弱网与首包延迟，是否需把上行切 Opus（关联 §11.16 / M7）。
  - 是否把部分重记忆操作（长期摘要）保留为「同步时由服务端补算」的可选降级路径（v1 选了端侧完整，但保留此后路）。
